## Completed: UOW-09 — Dynamic Geospatial Search & Google Places Gap-Fill Hydration

> Motivated by the product ask: buyers should be able to type ANY ZIP, street address, or city (e.g. "Pensacola, FL", not just the seeded demo cities) into the location search and have the map fly there with real dealership pins discovered live, not just the offline gazetteer from UOW-08.

- [x] **Task 9.1:** Added `GooglePlacesGeocoder` to `@nemzilla/spatial-core`'s `src/geocoder.ts` — a `GeocoderResolver` backed by the Google Places (New) `places:searchText` endpoint, resolving a free-form query to `{ lat, lng, displayName, formattedAddress, boundingBox }`. Extended `GeocodedPoint` with those optional fields (non-breaking for `NullGeocoder`). Dependency-injectable `apiKey`/`fetchImpl`, short-circuits to `null` with no network call when no `apiKey` is configured — matching the stack's existing pluggable-fallback convention. Exported from `index.ts`. 11 new tests in `tests/geocoder.test.ts` including a Pensacola, FL fixture (`30.4213, -87.2169`).
- [x] **Task 9.2:** Added `geocodeLocationQuery(text, options)` to `src/adapters/locationAdapter.js`: tries the offline gazetteer (`resolveLocationQuery`) first — fast, deterministic, no network — then falls back to live `GooglePlacesGeocoder` resolution for anything the gazetteer misses (e.g. "Pensacola, FL", "32501", a street address). Returns `{ lat, lng, label, formattedAddress, boundingBox }` or `null`. `resolveGooglePlacesApiKey()` added, mirroring `chatFilterAdapter`'s `apiKey` → `GOOGLE_PLACES_API_KEY` env var → `window.CARBOYZ_GOOGLE_PLACES_API_KEY` resolution order.
- [x] **Task 9.3:** Wired `geocodeLocationQuery` into `MapView.js`'s location search modal (`buildLocationModal`): submit handler is now async with a "Searching…" busy state (input/button disabled mid-request); on success `map.flyTo` + `applyUserLocation` as before, on failure the same inline error UI (copy updated to mention street addresses).
- [x] **Task 9.4:** Added the dynamic H3 cell hydration trigger to `MapView.js`: a `SpatialCellIndex` (10-minute TTL) + `GooglePlacesAdapter` (`car_dealer`) instance per map view. `map.on('moveend'/'zoomend', ...)` derives the H3 cell under the current center and, when unhydrated or stale (`isCellFresh`), fires `discoverNearby()` — the "Look Far" gap-fill pipeline — merging newly-discovered dealer nodes into the rendered dealer pool (deduped by id against seeded/vendor dealers) via a new `dealerFromDiscoveredFeature()` helper in `carboyzAdapter.js`. A search-driven `flyTo` also ends in `moveend`, so search and viewport panning share one trigger path. No-ops (no network call) without a configured Places API key.
- [x] **Task 9.5 (bug fix, discovered during Playwright verification):** Both `GooglePlacesGeocoder` and `GooglePlacesAdapter` stored the native `fetch` reference as an instance property and invoked it as `this.fetchImpl(...)` — an unbound method call. Real browsers throw `TypeError: Illegal invocation` for native `fetch` called this way (it requires `this === window`), which silently broke both the live geocoder and the gap-fill pipeline in an actual browser despite passing under Node's mocked-`fetchImpl` unit tests. Fixed by binding to `globalThis` in both constructors regardless of source (`(fetchImpl ?? fetch).bind(globalThis)`).
- [x] **Task 9.6:** Added 10 tests to `tests/locationAdapter.test.js` (`resolveGooglePlacesApiKey` resolution order, `geocodeLocationQuery` offline short-circuit / live fallback for Pensacola-style and ZIP queries / no-apiKey no-network / blank-input no-network / empty-Places-result / network-failure-resolves-null) and 2 tests to `tests/carboyzAdapter.test.js` for `dealerFromDiscoveredFeature`. `npm test`: 191/191 pass. Coverage: `locationAdapter.js` 100% line / 88.89% branch, `carboyzAdapter.js` 96.26% line / 90.70% branch (both ≥80% gate).
